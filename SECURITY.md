# Политика безопасности — ЭтерисBot

Мы серьезно относимся к безопасности. Если вы обнаружите уязвимость, пожалуйста, следуйте политике ниже, чтобы мы могли безопасно провести оценку и устранить проблему.

## Общие сведения / Информация о самостоятельном хостинге (Self-hosting)

"ЭтерисBot" распространяется как программное обеспечение с открытым исходным кодом для самостоятельного хостинга. Мы (сопровождающие проекта) не управляем экземплярами на селф-хостинге и не имеем доступа к пользовательским данным или конфигурациям на сторонних развертываниях. Владельцы селф-хостинга сами несут ответственность за безопасность и работу своих серверов. Данная политика описывает, как сообщать об уязвимостях, затрагивающих код проекта, и содержит рекомендации для владельцев селф-хостинга, обнаруживших проблемы безопасности в своем развертывании.

## Как сообщить об уязвимости (предпочтительный способ)

* Предпочтительный канал: Создайте приватную консультацию по безопасности (Security Advisory) на GitHub для этого репозитория (рекомендуется).
* Если вы не можете использовать GitHub Advisories, откройте тикет: https://
* ЗАПРЕЩАЕТСЯ открывать публичные issue с деталями эксплойта.

Если вы обнаружили проблему в вашем самостоятельно развернутом экземпляре, которая, по всей видимости, вызвана неправильной настройкой, сначала свяжитесь с оператором/хостером экземпляра. Если вы считаете, что проблема вызвана уязвимостью в коде TitanBot, выполните шаги по отправке отчета выше и укажите, исходит ли отчет от экземпляра на селф-хостинге.

## Сроки реагирования (чего ожидать)

* Подтверждение: в течение 72 часов.
* Сортировка (Triage) и оценка серьезности: в течение 7 дней.
* План исправления/миграции:
* Критический уровень: стремимся выпустить исправление или временное решение в течение 7–14 дней.
* Высокий уровень: стремимся выпустить в течение 30 дней.
* Средний/Низкий уровень: будет устранено в будущем релизе; сообщим в течение 90 дней.


* Публичное раскрытие: мы скоординируем действия с автором отчета и обычно публикуем уведомление после выпуска патча или в течение 90 дней, если проблема не решена (если автор отчета не попросит об обратном).

## Правила безопасного тестирования (правила взаимодействия для исследователей)

* Тестируйте только те сервисы, которыми вы владеете или на тестирование которых у вас есть явное разрешение.
* Не извлекайте, не уничтожайте и не изменяйте пользовательские данные.
* Не пытайтесь повысить привилегии или получить доступ к токенам пользователей Discord, личным сообщениям (DM) или другому приватному пользовательскому контенту.
* Предоставьте минимальный, безопасный PoC (доказательство концепции), который воспроизводит проблему. Скройте конфиденциальные данные (токены, персональные данные).
* Если уязвимость требует агрессивного тестирования, сначала свяжитесь с нами, чтобы согласовать план.

## Что включить в ваш отчет

* Затронутый компонент (например, миграция базы данных, парсер команд, OAuth).
* Четкие, минимальные шаги для воспроизведения.
* Среда: SHA коммита, тег релиза или версия.
* Наблюдалась ли проблема на селф-хостинг развертывании (и конфигурация этого развертывания).
* PoC (скрипт, HTTP-запрос, логи, скриншоты) — удалите секретные данные перед отправкой.
* Влияние (утечка данных, повышение привилегий, удаленное выполнение кода и т.д.).
* Предлагаемые меры по смягчению последствий (если есть).
* Контактная информация для обратной связи.

## Сообщения об инцидентах в селф-хостинг развертываниях

Если вы управляете экземпляром TitanBot на собственном сервере и столкнулись с инцидентом безопасности:

* Немедленно смените (ротируйте) все скомпрометированные секреты (токен бота, учетные данные БД, API-ключи).
* Сделайте снимок логов/конфигурации для расследования (избегайте передачи секретов).
* Если вам нужна помощь с основным кодом (upstream), создайте приватное уведомление о безопасности и приложите очищенные от секретов шаги воспроизведения, а также версию/коммит TitanBot.
* Сопровождающие могут исправлять уязвимости только в основном коде; мы не можем менять токены, восстанавливать данные или устранять проблемы на серверах других хостеров.

## Безопасность Redis

### Upstash Redis

При использовании сервисов Redis:

* Upstash Redis использует REST API с аутентификацией на основе токенов
* Всегда используйте полный URL для подключения с учетными данными из панели управления Upstash
* Смените токены доступа Redis, если есть подозрение на их компрометацию

## Область действия (Scope)

* Входит в область действия: код этого репозитория, процессы аутентификации, вебхуки, предоставляемые этим проектом, и целевые артефакты развертывания (скрипты).
* Не входит в область действия: сторонние сервисы (сам Discord, хостинги баз данных) и экземпляры, которыми вы не владеете, без согласия их владельца.

## Советы по обслуживанию и усилению защиты для селф-хостеров (рекомендуемые настройки)

* Используйте TLS для всех открытых эндпоинтов и вебхуков (Let’s Encrypt вполне подойдет)
* Не открывайте доступ к Postgres из публичного интернета. Используйте внутреннюю сеть, VPC или SSH-туннели
* Запускайте Postgres с аутентификацией, надежными паролями и сетевыми ограничениями
* Не храните секреты в репозитории (используйте переменные окружения, менеджеры секретов или GitHub Secrets для CI)
* Ограничьте интенты (intents) и разрешения бота в Discord до минимально необходимых
* Включите автоматическое обновление зависимостей (Dependabot) и оповещения о безопасности
* Включите сканирование секретов для вашего репозитория(ев) и защиту от пуша (push protection), если доступно
* Меняйте токены бота и API-ключи при подозрении на компрометацию
* Регулярно делайте бэкапы Postgres и периодически тестируйте их восстановление
* Отслеживайте логи и настройте оповещения о подозрительной активности (неожиданные изменения конфигурации, массовые удаления)
* Используйте файлы `.env` для всех секретов Redis и баз данных, никогда не коммитьте их

## Руководство по внедрению Upstash Redis

При развертывании с использованием сервисов кэширования:

1. **Настройка Redis**:
* Используйте бессерверную базу данных Upstash Redis
* Фронтенд и бэкенд могут получать доступ через REST API
* Соединение автоматически защищено через HTTPS/TLS


2. **Переменные окружения**:
```env
UPSTASH_REDIS_REST_URL=https://redis.upstash.io/your-id
UPSTASH_REDIS_REST_TOKEN=your-token

```


3. **Лучшие практики безопасности**:
* Никогда не храните токены Redis в открытом виде в конфигурациях развертывания
* Используйте менеджеры секретов среды развертывания для учетных данных
* Регулярно меняйте токены Upstash в панели управления сервисом
* Мониторьте использование соединений Redis через логи панели управления


4. **Стратегия кэширования**:
* PJMEans добавляет 5-минутный TTL (время жизни) к кэшированному ответу
* Lrucache используется для передачи данных серверной статистики
* Включите события `save` для функций затухания хэшей (hash decay)

## Конфиденциальность и телеметрия

* По умолчанию TitanBot не отправляет данные на сторонние серверы ("phone home") и не собирает данные об использовании. (Если вы планируете добавить телеметрию, она должна быть добровольной (opt-in), задокументированной и прозрачной).
* Сопровождающие не получают данные с экземпляров на селф-хостинге. Если вы решите включить какую-либо телеметрию, задокументируйте, что именно собирается и как от этого отказаться.
